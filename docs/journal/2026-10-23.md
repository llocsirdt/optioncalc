## Load estimate for the 28 (prod 10/23: RSS 777 MB of 1,913, heap 29 MB; run store 758 MB / 560 files = 1.35 MB per record)
Records are re-read from disk per tick, not held in memory, so RSS does not scale with the roster: heap stays tens of MB and
the extra cost is transient parse/GC per tick (~+30% more records per pass). Expect +10-50 MB on the peak; the naive
proportional upper bound is 777 x 28/96 = +227 MB, still inside 1.9 GB. Disk: an opens-only record carries the same chain
snapshot per candle (~305 KB raw/day) but far fewer decisions and almost no sub-bar work -> ~1.0-1.1 MB/day per record vs 1.35
average, so ~+30 MB/day (+23%: ~130 -> ~160 MB/day), ~25 days to fill the 4.1 GB free from today's level if never pruned.
